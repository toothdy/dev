# CRUD 自定义更新输入归一化设计

- 日期：2026-07-29
- 项目：`cool-admin-go-next`
- 状态：已批准，待实施

## 1. 背景

通用 CRUD 的默认更新会根据资源元数据忽略只读字段，并由服务端维护 `update_time`。但是，当资源 Service 实现 `crud.UpdateHandler` 时，`Runtime.Update` 和 `Runtime.UpdateMany` 会把只经过租户字段净化的请求直接交给自定义服务，跳过默认更新的只读字段处理。

菜单服务曾局部删除 `createTime` 和 `updateTime`，参数服务没有同样的防御。因此，前端把详情结果原样提交到参数更新接口时，自定义字段白名单会返回 `未知字段: updateTime`。这是 CRUD 默认实现与自定义扩展点之间的契约不一致。

日志保留时间接口 `/admin/base/sys/log/setKeep` 是独立自定义路由，不经过 CRUD。它使用 GoFrame Model 更新 `base_sys_conf`。项目将 `update_time` 配置为自动维护字段，但数据库列类型为 `varchar`；GoFrame v2.10.2 的自动类型分派不支持为字符串字段生成时间值，最终产生 `update_time = NULL`。

## 2. 目标

1. 让默认更新和自定义 `UpdateHandler` 获得一致的只读字段语义。
2. 保留更新主键，使自定义服务仍能定位目标记录。
3. 同时覆盖单条更新和批量更新。
4. 不允许客户端通过自定义更新修改租户、时间或资源声明的其他只读字段。
5. 修复系统配置更新写入空更新时间的问题。
6. 不改变现有更新路由、返回值、事务和租户作用域。

## 3. 非目标

1. 不移除菜单和部门现有的模块内只读字段防御。
2. 不把参数、菜单、部门等自定义更新重写为默认 CRUD。
3. 不修改前端详情表单的提交结构。
4. 不改变数据库时间字段类型或执行数据库迁移。
5. 不扩大到新增、删除和查询扩展点。

## 4. 方案比较

### 4.1 通用 CRUD 边界归一化，采用

CRUD Runtime 在派发更新前基于资源元数据创建净化后的输入副本：保留主键，删除其余只读字段，再传给默认实现或自定义 `UpdateHandler`。该方案一次覆盖所有现有和后续自定义更新，并保持统一契约。

### 4.2 各 Service 局部删除字段，不采用

在参数服务中复制菜单的 `delete` 逻辑改动最小，但每个新自定义服务仍可能重复遗漏，无法修复公共扩展点契约。

### 4.3 要求前端不提交只读字段，不采用

前端可以减少冗余字段，但不能作为后端写保护。不同客户端、批量接口或旧版本页面仍可提交完整详情对象。

## 5. 更新请求契约

归一化后的自定义更新请求遵循以下规则：

| 字段 | 行为 |
| --- | --- |
| 资源主键，如 `id` | 保留，供自定义服务定位记录 |
| `createTime`、`updateTime` | 删除，由服务端维护 |
| `tenantId` | 按现有租户净化规则删除 |
| 资源声明的其他只读字段 | 删除，不交给自定义服务 |
| 可写业务字段 | 保留原值，包括 `false`、`0`、空字符串和显式 `null` |
| 未在资源元数据中的字段 | 保留，由自定义服务继续执行严格白名单校验 |

未知字段不能在公共层静默删除，否则会掩盖拼写错误。只有明确声明为只读的字段会被净化。

## 6. 实现设计

### 6.1 公共输入归一化

在 `cool/crud/runtime.go` 增加更新输入归一化函数：

1. 复用现有租户净化逻辑创建请求副本。
2. 遍历 `resource.ReadonlyFields`。
3. 跳过 `resource.PrimaryField.JSONName`，保留主键。
4. 删除其余只读字段。
5. 返回副本，不修改调用者传入的 map。

`Runtime.Update` 在租户作用域校验后调用该函数，再判断是否存在自定义 `UpdateHandler`。`Runtime.UpdateMany` 对每一项使用同一函数，保证单条和批量契约一致。默认更新继续接收归一化后的数据，其 SQL 行为不变。

### 6.2 现有自定义服务

参数服务不再收到 `createTime`、`updateTime` 和 `tenantId`，现有未知字段校验继续拒绝真正未知的字段，并继续通过 `mutationTimestamp()` 写入服务端更新时间。

菜单、部门现有的局部 `delete` 保留。它们对直接调用 Service 的场景仍是防御，并且在 CRUD Runtime 已归一化时不会产生副作用。

### 6.3 系统配置更新时间

`ConfService.UpdateValue` 不依赖 GoFrame 对 `varchar update_time` 的自动时间推断。配置更新数据显式包含：

1. 新的 `c_value`。
2. `mutationTimestamp()` 生成的 `update_time`。

更新不再重复把条件键 `c_key` 写回自身。SQL 的 `WHERE c_key = ?` 和现有错误包装保持不变。

## 7. 错误与安全边界

1. 主键缺失或非法仍由自定义服务返回现有校验错误。
2. 真正未知的字段仍到达自定义服务并被拒绝。
3. 客户端只读字段被静默忽略，与默认 CRUD 当前行为一致。
4. 租户字段继续由现有 `sanitizeTenantMutationInput` 和租户作用域共同保护。
5. 配置更新失败继续使用 `gerror.Wrap` 保留错误栈。

## 8. 测试设计

### 8.1 CRUD Runtime 单元测试

在现有 override 测试中覆盖：

1. 单条自定义更新保留 `id` 和业务字段。
2. `createTime`、`updateTime`、`tenantId` 不会到达 Handler。
3. 资源额外声明的只读字段不会到达 Handler。
4. 未知字段仍会到达 Handler，供业务白名单校验。
5. 原始输入 map 不被修改。
6. 批量更新对每一项应用相同规则。

### 8.2 参数服务回归

通过 CRUD Runtime 提交包含详情只读字段的参数更新请求，确认不再返回未知字段，并确认自定义参数更新仍接收到主键和业务字段。

### 8.3 配置服务回归

使用 GoFrame DryRun 或现有数据库测试设施断言配置更新 SQL：

1. 包含非空 `update_time`。
2. 更新 `c_value`。
3. 不在 `SET` 中重复更新 `c_key`。
4. 保留 `WHERE c_key = ?`。

相关包测试通过后，再运行完整 `go test ./... -count=1`。数据库集成测试只在现有环境开关可用时执行。

## 9. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 删除主键导致自定义更新无法定位记录 | 归一化时显式保留资源主键并加入测试 |
| 误删自定义服务用于校验的未知字段 | 只删除资源明确声明的只读字段 |
| 单条与批量行为漂移 | 两条派发路径调用同一归一化函数 |
| 修改调用者 map 产生隐藏副作用 | 基于现有 clone 语义返回副本并测试 |
| GoFrame 再次覆盖显式更新时间 | 配置更新显式提供非空字段，并对生成 SQL 做断言 |

## 10. 验收标准

1. 参数完整编辑表单包含 `createTime`、`updateTime`、`tenantId` 时可以正常更新。
2. 自定义 `UpdateHandler` 收到主键和可写字段，但收不到其他只读字段。
3. `Update` 与 `UpdateMany` 行为一致。
4. 未知字段校验和租户隔离不弱化。
5. 菜单、部门现有更新行为不回归。
6. `/admin/base/sys/log/setKeep` 更新生成非空 `update_time`。
7. 相关单元测试和全量测试通过。
