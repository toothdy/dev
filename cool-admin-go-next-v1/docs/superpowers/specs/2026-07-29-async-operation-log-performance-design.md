# 异步操作日志与刷新性能优化设计

## 目标

降低 `/admin/base/comm/person` 与 `/admin/base/comm/permmenu` 的 Go 后端 TTFB，同时保持现有操作日志字段、脱敏规则和租户归属不变。

本次优化解决两个已通过 Chrome DevTools MCP 验证的问题：

- Go 操作日志在业务处理前同步写入 `base_sys_log`，直接增加接口 TTFB。
- Go 本地数据库配置开启 SQL debug，而 Node 本地配置关闭了 SQL logging。

## 日志边界

`base_sys_log` 是操作日志，只记录用户、接口、IP、参数和租户等操作信息。它不记录业务异常、panic、SQL 错误或系统运行错误。

系统错误继续由现有错误中间件和 `g.Log()` 处理。异步操作日志写入失败只输出到系统日志，不回写操作日志，不改变业务响应。

## 方案选择

采用模块级有界内存队列和单后台 worker。

不采用以下方案：

- 每个请求启动一个 goroutine：并发无上限，缺少停机协调，容易在流量突增时放大数据库压力。
- Redis、Kafka 等外部队列：当前后台管理场景不需要额外基础设施和投递保证。
- 跳过 GET 操作日志：会改变现有日志覆盖范围，不符合保留全部操作日志的目标。

## 组件设计

### Base 日志 Runtime

`base` 模块注册一个随应用启动和停止的 Runtime。Runtime 持有日志队列、后台 worker、同步日志服务和生命周期状态。

- 默认队列容量为 `1024`。
- `Start` 启动一个 worker。
- `Submit` 捕获不可变的操作日志数据和租户作用域，并以非阻塞方式入队。
- worker 继续复用现有 `LogService.Record` 完成单条数据库写入。
- `Stop` 停止接收新日志，并在最多 `5s` 内等待队列刷完。

中间件只负责构建和脱敏 `LogRecordRequest`，调用 `Submit` 后立即进入后续中间件和业务处理，不等待数据库结果。

### 租户作用域

请求 Context 在响应结束后会被取消，不能直接交给后台数据库写入。`Submit` 在请求期间解析租户作用域，队列项只保存必要的租户信息，不持有完整 HTTP 请求。

worker 使用自身生命周期 Context 重建租户作用域：租户请求使用捕获的租户 ID，平台和匿名请求使用跨租户内部作用域，使写入结果继续符合现有 `tenant_id` 规则。

### 溢出和失败

`Submit` 不等待空闲队列位置。队列满时丢弃最新日志并增加丢弃计数，保证业务请求不会因日志系统产生背压。

为避免日志风暴，队列溢出只按受控频率输出系统警告。每条数据库写入使用独立的超时 Context，默认超时为 `2s`；单条写入超时或失败时由 worker 输出系统错误并继续消费下一条日志。

worker 在单条日志边界恢复 panic，通过 `g.Log()` 记录错误和调用栈，然后继续消费后续日志。写入失败、超时和 panic 都不进入 `base_sys_log`，也不影响业务响应。

### 提交时机

中间件在进入后续业务前构建并脱敏操作日志请求，通过 `defer` 在后续中间件和业务处理结束后提交队列。

- 正常返回、业务错误和 panic 都会触发同一次提交。
- 操作日志仍保持原有字段和接口契约，不增加状态、业务码或耗时字段。
- `/admin/base/sys/log/clear` 在清理完成后才提交自身操作日志，避免该记录被本次清理删除。
- 业务错误和 panic 的详细信息仍只由错误边界写入系统日志，不写入操作日志。
- 提交仍为非阻塞入队，不等待数据库写入，也不改变业务响应。

## 数据库调试配置

默认配置将 `database.default.debug` 设为 `false`，与 Node 本地 `logging: false` 保持一致。

该配置只关闭 GoFrame ORM 的 SQL 调试输出，不关闭 `base_sys_log` 操作日志。

## 保留期清理

对齐 Node 版 `BaseLogJob` 的每日清理行为，让 `base_sys_conf.logKeep` 配置真正生效。

- 每日零点执行一次，不在应用启动时立即清理。
- 每次执行重新读取 `logKeep`，以当前时间减去保留天数后当天 `00:00:00` 作为截止时间。
- 跨租户删除 `create_time` 早于截止时间的操作日志。
- 每批最多删除 `1000` 条，避免历史数据较多时形成单次大事务。
- `logKeep` 缺失、无法解析或不是正整数时停止本轮清理并输出系统错误，不采用 Node 版清空整表的回退行为。
- 清理开始、完成、失败和耗时只通过 `g.Log()` 输出系统日志，不写入 `base_sys_log`，也不影响请求处理。
- 每轮清理使用独立的超时 Context，默认超时为 `30m`；超时后停止后续批次并输出系统错误。
- 同一实例只允许一轮清理执行；上次清理尚未结束时跳过本轮，并通过 `g.Log()` 输出系统警告。
- 清理任务在单次执行边界恢复 panic，通过 `g.Log()` 记录错误和调用栈，避免定时任务 panic 导致进程退出。
- 手动清空接口保持现有租户作用域和行为不变。

## 配置

在 `module.base.middleware.log` 下保留 `enable`，并增加：

- `queueSize: 1024`
- `shutdownTimeout: 5s`
- 可选的 `writeTimeout`，未配置时由代码使用默认值 `2s`
- 可选的 `cleanupTimeout`，未配置时由代码使用默认值 `30m`

`writeTimeout` 和 `cleanupTimeout` 都不写入默认 YAML；用户显式配置时覆盖代码默认值。配置加载时拒绝非正数队列容量、停机超时、写入超时和清理超时，避免运行时产生无界、无法退出或失去超时保护的行为。

## 测试

Go 测试覆盖：

- 中间件提交日志后不等待数据库写入。
- 中间件在业务处理完成后提交日志，正常返回和 panic 均只提交一次。
- 清空操作日志完成后再提交清理操作记录。
- 请求参数脱敏和大小限制保持不变。
- 租户、平台和匿名操作日志保持正确归属。
- 队列满时 `Submit` 立即返回并记录丢弃。
- 正常停止会刷完已接收日志。
- 写入失败只进入系统日志路径，不改变 HTTP 响应。
- 单条写入超时后 worker 继续消费下一条日志。
- 单条写入 panic 被恢复并写入系统日志，worker 继续消费下一条日志。
- 未配置 `writeTimeout` 时使用 `2s`，显式非正数配置会被拒绝。
- Base Runtime 正确注入日志中间件，关闭日志开关时不记录。
- `logKeep` 截止日期按本地时区当天零点计算。
- 过期操作日志跨租户分批删除，边界时刻和更新日志得到保留。
- 非法保留天数不会删除任何操作日志。
- 定时清理随 Base Runtime 启停，清理失败不会停止操作日志 worker。
- 清理超时后任务正常退出，未到期批次不会继续执行。
- 清理 panic 被恢复并写入系统日志，不会终止进程或后续定时任务。
- 上一轮清理仍在运行时跳过重复执行。
- 未配置 `cleanupTimeout` 时使用 `30m`，显式非正数配置会被拒绝。

浏览器验证覆盖：

- 真实刷新中两条接口的 TTFB 重新采样。
- Vite 排队和 `Connection: close` 作为已知前端链路开销单独报告，不计入本轮后端验收。

## 验收标准

- 操作日志数据库写入不再位于业务响应关键路径。
- 操作日志字段、脱敏规则、路由范围和租户语义不变。
- `logKeep` 配置控制每日过期日志清理，且非法配置不会触发删除。
- 数据库 SQL debug 默认关闭，操作日志仍正常写入。
- Go 单元测试和相关集成测试通过。
- 浏览器热刷新时 `person` 与 `permmenu` 不再出现由同步操作日志造成的额外 TTFB。

## 非目标

- 不为操作日志增加状态、耗时或错误字段。
- 不修改业务异常和系统日志处理机制。
- 不引入 Redis、消息队列或批量日志表结构。
- 不在本次优化中缓存 `person` 或 `permmenu` 响应。
- 不修改 Vite 代理或其他前端代码。
