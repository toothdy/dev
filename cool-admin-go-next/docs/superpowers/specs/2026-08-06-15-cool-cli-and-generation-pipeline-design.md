# 模块 15：Cool CLI 与生成流水线设计

> 日期：2026-08-06
> 状态：待复核
> 模块：15 Cool CLI 与生成流水线
> 对应拆分项：15.1-15.10
> 前置模块：12 Provider 依赖图、13 Descriptor 与 DO 代码生成、14 静态模块注册表生成

## 1. 目标

模块 15 将模块 11-14 已批准的源码分析、Provider 图、Descriptor 编译和静态注册表渲染能力串成统一、可复用的内存流水线，并通过独立的 `cmd/cool` 入口提供 `cool generate` 与 `cool check`。

`cool generate` 只有在分析、生成、格式化和 Go 类型检查全部成功后，才原子替换唯一目标 `modules/modules_gen.go`。`cool check` 复用同一流水线验证当前已冻结的规则、候选源码稳定性和已提交生成文件新鲜度，全程不修改工作区。

本模块不复制模块 12-14 的领域规则，也不把 `cool check` 变成 `gofmt`、`go vet` 或 `go test` 的包装器。

## 2. 前置门禁

模块 15 开始实施前，模块 12-14 必须按各自已批准设计和实施计划完整交付，而不只是现有测试恰好通过。至少确认：

- 模块 12 已实现跨模块具体 Provider 与目标模块 `contract/**` 接口匹配、Config/Seed 隔离、参数级位置、完整依赖与循环路径、模块图投影和稳定拓扑；
- 模块 13 已完整校验实体、Schema、字段标签和物理名称，并稳定产出 Descriptor/DO 片段；
- 模块 14 已稳定渲染当前已冻结的模块、Descriptor 和普通 Provider 注册表，且只返回内存字节；
- 三个模块均不执行业务函数、不连接数据库、不写生成文件；
- `go test ./cool-next/codegen ./cool-next/core/module -count=1` 和对应 Race Test 通过。

若前置模块存在契约缺口，必须回到原拥有模块修复并补测试。模块 15 不得用额外的 CLI 特判掩盖缺口，也不得对尚未实现的检查宣称成功。

## 3. 共享内存流水线

`generate` 与 `check` 共用同一套内存流水线，但流水线明确分成“构建候选”和“验证候选”两个阶段：

```text
构建候选：
规范化工作区根目录
-> 使用占位 Overlay 分析源码
-> 编译 Descriptor 与 DO 片段
-> 将生成 Descriptor Provider 纳入并校验 Provider 图
-> 渲染静态模块注册表
-> 再次使用 go/format 规范化候选源码
-> 返回候选源码字节

验证候选：
使用候选 Overlay 执行 Go 类型检查
```

`generate` 构建一次并验证一次，随后原子提交；`check` 独立构建两次并先比较稳定性，再验证其中一份候选，最后比较已提交文件的新鲜度。该分层避免为了稳定性检查重复执行昂贵的类型检查，同时保证两个命令使用完全相同的构建与验证规则。

流水线的公开选项只接受工作区根目录。模块目录固定为 `modules`，目标固定为 `modules/modules_gen.go`，不得通过 CLI 参数或公开选项改写，以保持 Cool 生成器只有一个输出的架构不变量。

`Render` 当前已经调用 `go/format`，流水线仍在提交边界再次格式化。这样格式化是模块 15 的显式成功条件，后续渲染器拆分或增加片段时不会绕过该门禁。

任一阶段失败都返回稳定诊断并立即停止；失败候选不进入写入阶段。流水线不读取应用运行配置，不执行 `ModuleConfig`、Schema 函数或构造器，也不建立数据库连接。

## 4. 两类 Overlay

### 4.1 分析旧产物的占位 Overlay

源码分析使用 `go/packages` 加载 `modules/...`。如果已提交的 `modules/modules_gen.go` 引用了已删除的实体、构造器或包，直接加载会让旧产物阻塞重新生成，破坏生成器的自愈能力。

因此流水线调用分析器时，必须把目标路径 Overlay 为以下最小源码：

```go
package modules
```

该 Overlay 只用于隔离旧 Cool 产物，不覆盖业务模块源码、protobuf 文件或第三方生成文件。公开的 `Analyze` 行为保持兼容；实现可增加包内分析入口，把受控 Overlay 传给现有 `packages.Load`。

测试必须覆盖旧生成文件语法损坏、引用已删除符号以及目标文件尚不存在三种情况，证明分析只依赖真实业务源码而不依赖旧输出。

### 4.2 候选源码的类型检查 Overlay

渲染和格式化完成后，第二次独立调用 `go/packages`，把同一目标路径 Overlay 为真实候选字节，并加载 `./modules` 包及其依赖的完整类型信息。

候选 Overlay 用于证明最终文件在当前工作区中可编译，必须捕获仅靠语法格式化无法发现的错误，例如导入包不存在、类型参数不匹配、构造器调用参数错误或 Graph 定义类型不兼容。类型诊断转换为相对工作区的稳定位置并排序。

占位 Overlay 与候选 Overlay 的目的、内容和加载时点不同，不能合并成一次加载：前者保证旧输出不阻塞分析，后者验证新输出真实可编译。

## 5. `cool generate` 与原子替换

`cool generate` 先完整取得并验证候选字节，再执行提交：

```text
在 modules/ 同目录创建唯一临时文件
-> 写入全部候选字节
-> 设置固定生成文件权限
-> Sync
-> Close
-> os.Rename 到 modules/modules_gen.go
```

临时文件必须与目标同目录，避免跨文件系统 Rename。任一写入、同步、权限或关闭错误都先删除临时文件并保留旧目标；Rename 失败同样清理临时文件。成功 Rename 是最后一个影响命令结论的文件系统步骤，之后不再执行会导致“命令失败但目标已改变”的操作。

目标已存在时替换完整旧文件，目标不存在时创建新文件。并发生成允许不同进程各自创建临时文件；确定性候选保证最终完整内容一致，不需要引入锁文件或常驻协调器。

## 6. `cool check`

`cool check` 严格只读，执行顺序为：

1. 从相同工作区输入生成第一份候选源码；
2. 再次独立运行分析和渲染，生成第二份候选源码；
3. 比较两份候选字节，任何差异都报告生成不稳定；
4. 对候选源码执行 Overlay 类型检查；
5. 读取 `modules/modules_gen.go`，与候选源码逐字节比较；
6. 文件缺失或字节不同均报告生成文件过期。

两次生成必须重新执行分析，不得复制第一份结果伪造稳定性检查。`check` 不创建目录、临时文件或目标文件，不自动修复格式和新鲜度。

当前实体元数据、模块配置声明、通用 Provider 图、跨模块依赖和静态注册表一致性由模块 11-14 的共享分析规则负责。后续模块应扩展同一源码模型和流水线阶段，使 `generate` 与 `check` 同时获得新规则；本模块不预建运行时插件注册器或另一套规则 DSL。

## 7. CLI 与退出码

独立入口固定为 `cmd/cool/main.go`。首期只暴露当前真实实现的命令：

```text
cool generate
cool check
```

退出码统一为：

| 退出码 | 含义 |
| --- | --- |
| `0` | 命令成功或显式请求帮助 |
| `1` | 分析、生成、类型检查、稳定性、新鲜度或文件提交失败 |
| `2` | 缺少命令、未知命令或参数用法错误 |

可测试的 `run` 函数接收 Context、参数、工作区目录及标准输出/错误输出，返回退出码；`main` 只创建可取消 Context、取得当前目录、调用 `run` 并执行 `os.Exit`。成功摘要写 stdout，诊断和用法错误写 stderr。

CLI 不提供可修改模块根目录或输出路径的参数。错误输出使用 codegen 稳定诊断，不打印敏感环境变量、配置内容或完整内部缓存路径。

## 9. 不提前实现的边界

本模块明确不实现：

- `cool build`、`cool run` 或固定成功占位，它们属于模块 46；
- `cool outbox list/show/replay`，它们属于模块 56；
- Controller、路由、生命周期、鉴权、gRPC、Outbox、Event、Schedule 或 Queue 的发现、校验和生成；
- Service 方法到 API 的动态映射；
- 数据库连接、Schema 探测、运行配置加载或业务函数执行；
- `cool check` 内部调用 `gofmt`、`go vet`、`go test` 或 `go test -race`；
- 自定义输出目录、多个 Cool 生成文件或业务模块内分散生成文件；
- 为未来规则设计插件系统、反射注册表或字符串规则定位器。

标准 protobuf 的 `*.pb.go` 和 `*_grpc.pb.go` 不属于 Cool 唯一输出限制，但模块 15 不负责调用 protobuf 工具。

## 10. 测试与验收

测试至少覆盖：

- 完整 AST/类型分析到唯一生成文件的 Golden；
- 旧生成文件无效时仍可生成，新候选无效时拒绝提交；
- 候选目标已存在和不存在时的 Overlay 类型检查；
- 格式化失败、类型检查失败和所有原子写入故障时旧字节不变；
- 临时文件与目标位于同一目录，失败后无临时文件残留；
- `check` 对缺失、过期、最新和不稳定输出的只读判断；
- 连续 `generate` 输出字节一致；
- CLI stdout/stderr、帮助和 `0/1/2` 退出码；
- 无数据库、无应用配置和无业务函数执行条件下生成成功；
- 未批准命令和组件类别没有被暴露或检查。

模块门禁为：

```bash
go test ./cool-next/codegen ./cmd/cool -count=1
go test -race ./cool-next/codegen ./cmd/cool -count=1
go run ./cmd/cool generate
go run ./cmd/cool check
git diff --exit-code -- modules/modules_gen.go
go test ./... -count=1
go vet ./...
make check
git diff --check
```

`cool check` 通过只表示 Cool 当前已冻结的静态规则、生成稳定性和生成文件新鲜度通过。标准 Go 命令继续作为独立门禁执行。
