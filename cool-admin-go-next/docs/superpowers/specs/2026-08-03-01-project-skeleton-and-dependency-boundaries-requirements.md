## 2. 目标与成功条件

模块 01 为其余 43 个模块建立共同工程基线：

1. 仓库根是可被 Go 工具链识别的唯一 Go Module；
2. 框架、业务、生成代码和应用入口具有明确的单向依赖边界；
3. `cool-next/**` 反向依赖 `modules/**` 时可被自动阻止；
4. 本地与 CI 执行同一套格式、静态检查、测试和 Race Test 契约；
5. MySQL、PostgreSQL、SQLite 具有可复用、隔离的集成测试环境。

成功条件是：从干净检出开始，不依赖开发者私有配置即可执行基础门禁；显式启用完整门禁后，三数据库 Smoke Test 全部通过并输出独立结果。

## 3. 范围

### 3.1 包含

- 初始化根 Go Module、Go 与 GoFrame 版本基线；
- 建立 `cool-next/`、`cmd/`、`modules/`、`manifest/` 等顶级目录；
- 定义目录所有权和 Go import 方向；
- 建立根级依赖边界守卫；
- 建立 Module、格式、静态检查、单测和 Race Test 门禁；
- 建立 MySQL、PostgreSQL、SQLite 集成测试 Harness；
- 建立 CI 入口、测试环境说明和验收证据。

### 3.2 不包含

- Exception、配置加载、模块声明、实体元数据等后续框架能力；
- `cool generate`、`cool check`、`cool build`、`cool run` 的实现；
- CRUD、HTTP、gRPC、鉴权、生命周期和 Outbox；
- 具体业务模块、业务表、初始化数据和示例业务；
- 数据库方言适配、Schema 同步和业务 DML；
- `main.go` 和应用装配；
- 生产部署拓扑、发布流程和性能阈值。

## 4. 技术基线

| 项 | 要求 |
|---|---|
| Go Module | `github.com/toothdy/cool-admin-go-next` |
| Go | `1.26` 语言基线，CI 固定明确的 `1.26.x` 补丁版本 |
| GoFrame | `github.com/gogf/gf/v2 v2.10.2` |
| MySQL | `8.x`，最低 `8.0`，仅支持 InnoDB 事务能力 |
| PostgreSQL | `9.5+`，UTF-8 |
| SQLite | `3.24+`，集成测试使用文件数据库 |

规则：

- Go 次版本以及 GoFrame minor/major 升级必须独立评审；
- patch 升级可以作为依赖维护变更，但必须通过完整门禁；
- 直接依赖必须有明确用途并固定版本；
- `go mod tidy` 后仓库不得产生未提交差异；
- 仓库不得提交指向开发者本地绝对路径的 `replace`。

## 6. 功能需求

### 6.1 Go Module 与版本

#### M01-FR-001 根 Module

- 仓库根必须包含唯一 `go.mod`；
- Module Path 必须为 `github.com/toothdy/cool-admin-go-next`；
- 子目录不得建立独立 Go Module；
- 模块解析失败必须阻止合并。

#### M01-FR-002 版本固定

- `go.mod` 必须声明 Go 1.26 基线；
- GoFrame 必须固定为 v2.10.2；
- CI 使用确定的 Go patch 版本，禁止浮动到未验证版本；
- 升级后必须重新执行完整门禁。

#### M01-FR-003 依赖一致性

- `go mod tidy` 后不得新增、删除或修改受管文件；
- `go mod verify` 必须成功；
- `go.sum` 必须随依赖变化提交；
- 不得提交无用途直接依赖、本地绝对路径替换或私有凭据。

### 6.2 目录与所有权

#### M01-FR-004 目录骨架

- 必须建立第 5 节定义的顶级目录；
- 占位文件不得包含可执行逻辑或未批准 API；
- 本模块不得创建 `main.go` 或 `cmd/cool` 空壳命令。

#### M01-FR-005 目录所有权

| 区域 | 所有权 |
|---|---|
| `cool-next/**` | 框架实现 |
| `cmd/**` | 可执行命令入口 |
| `modules/**` | 业务模块和未来生成模块图 |
| `manifest/config/**` | 可提交的配置模板，不含真实凭据 |
| `test/integration/**` | 跨包和外部基础设施测试 |
| `.github/workflows/**` | 持续集成入口 |
| `docs/**` | 设计、需求和实施计划 |

生产代码不得依赖 `test/integration/**`；`manifest/**` 不承载 Go 可执行逻辑。

### 6.3 依赖方向

#### M01-FR-006 根级 import 方向

```text
root main / cmd
        |
        +----> modules / generated graph
        |                |
        +----> cool-next <+
                    |
                    +----> GoFrame / 标准库 / 已批准基础依赖
```

| 区域 | 允许依赖 | 禁止依赖 |
|---|---|---|
| `cool-next/**` | 标准库、GoFrame、已批准基础依赖、其他框架包 | `modules/**`、`cmd/**`、根应用入口 |
| `modules/**` | `cool-next/**`、稳定模块 Contract、业务依赖 | `cmd/**`、根应用入口 |
| `modules/modules_gen.go` | 业务模块、`cool-next/**` | `cmd/**`、根应用入口 |
| `cmd/**`、未来根入口 | `cool-next/**`、生成模块图 | 被框架或业务模块导入 |
| `test/integration/**` | 框架和业务测试对象 | 被生产包导入 |

#### M01-FR-007 控制流与 import 分离

- Host 可以在运行时调用由入口传入的生成模块图；
- `core/app` 不得通过 import 主动取得 `modules`；
- 上位架构中的调用链不构成反向 import 授权。

#### M01-FR-008 依赖边界守卫

- 守卫必须分析 Go 包元数据或语法结构，不得只搜索文本；
- `cool-next/**` 的依赖闭包不得包含仓库 `modules/**`；
- 规则同时覆盖普通源码、平台文件、Build Tag 文件和 `_test.go`；
- 跨边界黑盒测试必须放入 `test/integration/**`；
- 违规输出至少包含导入方、被导入包和命中规则；
- 可取得依赖链时必须同时输出链路。

#### M01-FR-009 守卫自测

守卫必须用测试夹具验证：

- 合法依赖通过；
- `cool-next -> modules` 直接依赖失败；
- 通过仓库中转包形成的间接依赖失败；
- `_test.go` 违规失败；
- Build Tag 文件违规失败；
- 别名导入不能绕过规则。

仓库尚无 `cool-next` Go 包时，守卫应明确报告仅完成骨架检查，不得声称已验证完整依赖闭包。

### 6.4 质量门禁

#### M01-FR-010 统一入口

- 本地和 CI 必须调用相同检查入口；
- 必须支持快速门禁和完整门禁；
- 任一阶段失败时整体返回非零退出码；
- 输出必须指出失败阶段和定位信息。

#### M01-FR-011 快速门禁

快速门禁至少包括：

1. `go mod tidy` 差异检查；
2. `go mod verify`；
3. `gofmt` 差异检查；
4. `go vet ./...`；
5. 依赖边界守卫；
6. `go test ./...`。

CI 中的格式与 Module 检查不得静默修改工作区后继续成功。

#### M01-FR-012 完整门禁

完整门禁必须包含快速门禁，并增加：

- `go test -race ./...`；
- MySQL、PostgreSQL、SQLite 集成 Smoke Test；
- 三数据库独立结果报告。

Race Test 在支持 Race Detector 的 Linux 环境执行，并显式满足所需 CGO 条件。

#### M01-FR-013 CI 行为

- Pull Request 和主分支提交必须执行完整门禁；
- 定时任务和发布检查必须执行最低版本与当前批准版本兼容性矩阵；
- 缓存只能复用依赖和编译产物，不得缓存测试通过结果；
- 失败日志不得输出 Token、密码、Secret 或完整 DSN；
- 相同提交重复执行应得到相同结论。

`cool check` 和 `cool build` 在对应后续模块实现前不得进入门禁，也不得用固定成功的占位命令模拟。

### 6.5 三数据库 Harness

#### M01-FR-014 统一 Harness

- 本地和 CI 使用同一份版本化环境定义；
- 三数据库使用同一测试接口和断言逻辑；
- 后续模块只能增加用例，不复制数据库启动与清理逻辑；
- 环境必须提供启动、Readiness、执行、收集结果和清理能力；
- Readiness 不得依赖固定时长等待。

#### M01-FR-015 隔离与配置

- MySQL、PostgreSQL 使用隔离的临时实例、数据库或 Schema；
- SQLite 使用独立临时文件，不得使用共享内存数据库代替并发环境；
- 地址、端口、用户和密码由测试环境注入；
- 每次运行使用唯一资源名称，支持重复和并行执行；
- 成功、失败和取消后均清理临时资源；
- 不得连接开发、预发布或生产数据库。

#### M01-FR-016 Smoke Test

每种数据库至少验证：

1. 通过 GoFrame `gdb` 建立连接并执行健康查询；
2. 读取实际数据库类型和版本；
3. 低于支持基线时明确失败；
4. 开启事务、写入并提交后数据可见；
5. 开启事务、写入并回滚后数据不可见；
6. 清理后无测试表或临时文件残留。

附加检查：

- MySQL 能使用 InnoDB；
- PostgreSQL 数据库编码为 UTF-8；
- SQLite 使用满足后续并发测试的文件数据库模式。

#### M01-FR-017 版本矩阵

| 执行层级 | 要求 |
|---|---|
| 每次合并 | 每种数据库运行一个已固定且满足基线的代表版本 |
| 定时与发布 | 同时覆盖最低支持版本和当前批准版本 |

版本矩阵必须记录实际版本，不允许使用无上限浮动标签。当前批准版本变化时必须走依赖维护评审。

#### M01-FR-018 自动化可验证

- 所有强制需求必须映射到自动化测试或检查；
- 无法自动化的条目必须说明人工证据、检查人和检查时机；
- 实施任务、测试名称和缺陷记录必须引用对应需求编号。

## 7. 非功能需求

| 编号 | 属性 | 要求 |
|---|---|---|
| `M01-NFR-001` | 可复现 | 干净环境可恢复依赖并得到一致检查结果 |

| `M01-NFR-006` | 可扩展 | 后续模块复用门禁与 Harness，只添加规则和用例 |
| `M01-NFR-007` | 确定性 | 重复和并行执行不受顺序或残留状态影响 |

本模块不冻结耗时、覆盖率和性能数值。首个可运行版本应记录基线，后续再独立批准回归阈值。

## 10. 完成定义

模块 01 只有同时满足以下条件才算完成：

- D-001-D-008 全部存在并通过评审；
- FR-001-FR-018 均有实现证据；
- NFR-001-NFR-008 均有检查或评审证据；
- AC-001-AC-018 全部通过；
- 快速门禁和完整门禁均可从干净检出执行；
- 三数据库结果可分别查看，失败不能被 Skip 掩盖；
- 仓库无凭据、本地绝对路径、测试残留和未提交生成差异；
- README 中的工程状态、执行入口和目录说明与实际交付一致；
- 不包含第 3.2 节明确推迟的后续模块实现；
- 文档状态经用户复核后从 `pending` 更新为 `reviewed`。

## 11. 后续模块约束

- 后续 43 个模块必须继承本模块的根级依赖禁令和质量门禁；
- 后续模块可以增加更严格的包级规则，不得放宽 `cool-next/**` 禁止依赖 `modules/**`；
- 后续数据库模块必须复用本模块 Harness，并在三数据库上添加相同行为用例；
- 模块 15 完成真实 `cool check/build` 后，才能将其加入强制门禁；
- 模块 46 才负责根应用入口和最终装配。

## 12. 变更控制

以下变更必须先回到本需求文档复核：

- Go Module Path、Go 基线或 GoFrame 版本策略变化；
- 新增顶级代码所有权目录；
- 放宽或改变根级 import 方向；
- 删除 Race Test 或任一数据库门禁；
- 改变最低数据库版本；
- 将后续模块能力提前并入模块 01。

仅修改脚本内部实现、CI 缓存方式或测试输出格式，且不改变需求行为时，可在实施计划中处理。
